# Groups at 1000 members: roles (1 owner + ≤50 admins), in-chat role-change system messages, group call UI

Research doc for the "1000-member groups" workstream. Every claim below is cited to the actual
source. Requirements under investigation: 1000-member cap enforced server-side; exactly one
owner (reassignable); up to 50 admins; in-chat system messages for role changes; E2EE preserved
at 1000 members (MLS — cite what e2e-core supports, no crypto redesign); group voice/video call
UI overhaul.

---

## 1. What exists today

### 1.1 Database schema — roles are a free-text binary, no owner, no cap

`database/migrations/005_conversations.sql:22-30`:

```sql
create table if not exists conversation_members (
    id              uuid primary key default gen_random_uuid(),
    conversation_id uuid not null references conversations(id) on delete cascade,
    user_id         uuid not null references users(id) on delete cascade,
    role            text not null default 'member',   -- admin | member
    joined_at       timestamptz not null default now(),
    left_at         timestamptz,                       -- null = active member
    unique (conversation_id, user_id)
);
```

- `role` is unconstrained text with only `'admin' | 'member'` used in practice. There is **no
  `owner` role, no CHECK constraint, no admin-count limit, and no member-count limit anywhere**
  (verified by grep across `database/migrations/*.sql` and `backend/api/src/routes/*.ts` — no
  cap constant exists).
- The `unique (conversation_id, user_id)` constraint is total (no nullable column inside it), so
  the known "Postgres NULL breaks upserts" bug class does not bite here; the
  `on conflict (conversation_id, user_id)` upsert in `conversations.ts:227-229` is safe.

### 1.2 Backend routes — creator becomes admin, no role management endpoints

`backend/api/src/routes/conversations.ts`:

- **Create group** (`POST /conversations/create`, lines 101-126): creator gets `'admin'`, everyone
  else `'member'` (line 115). **No member-count validation** — `member_ids` of any length is
  accepted, inserted in a per-member loop (lines 112-117).
- **Add members** (`POST /:id/members`, lines 203-233): caller must be an active `'admin'`
  (line 221). **No cap check.** Re-adding reinstates via `on conflict … do update set left_at = null`.
- **Remove member** (`DELETE /:id/members/:userId`, lines 239-259): admin removes anyone; a member
  may remove self.
- **There is no endpoint to change a member's role and no ownership concept.** Grep of
  `conversations.ts` shows `role` only in the caller-is-admin checks and the insert defaults.
- `GET /conversations/:id` (lines 174-196) returns members with `role`, so clients *could* render
  roles today.

### 1.3 MLS plumbing — server relays opaque bytes, delivery is per-user and destructive-on-read

`backend/api/src/routes/mls.ts`:

- `POST /mls/keypackages` stores one-time KeyPackages per device (lines 14-29); `GET
  /mls/keypackages/:user_id` **consumes one per active device** with `FOR UPDATE SKIP LOCKED` and
  409s when the pool is empty (lines 33-52). There is no replenishment signal — clients publish a
  fixed batch of 10 at bootstrap (`apps/ios/Voiid/Voiid/Networking/GroupEngine.swift:88`,
  `keyPackageBatch = 10`).
- `POST /mls/group-events` inserts one row **per (event, recipient_user_id)** in a loop (lines
  69-80). `GET /mls/group-events` returns all undelivered rows for the caller and marks **all of
  them delivered on first fetch** (lines 85-104) — keyed by `recipient_user_id`, not device.
  `database/migrations/011_mls.sql:21-33` confirms the schema (no `recipient_device_id`).

### 1.4 e2e-core — what the MLS layer supports (cited; NOT redesigning this)

`packages/e2e-core/src/group.rs`:

- OpenMLS 0.8 (`packages/e2e-core/Cargo.toml:40-43`) with the post-quantum X-Wing ciphersuite
  (`group.rs:30`).
- API surface: `create_group` (line 181), `join_group` (line 198), `add_member` (line 252 — one
  KeyPackage per call, commit merged locally), `remove_member` (line 308), `member_count`
  (line 337), `epoch` (line 350), `clear_pending` (line 363 — the building block for losing a
  concurrent-commit race), `encrypt`/`decrypt` (lines 374-411), `export_call_key` (line 416).
- **No member cap exists in the wrapper or in OpenMLS usage** — `add_member` can be called
  arbitrarily many times; RFC 9420 trees scale to 2^32 leaves with O(log n) path updates.
  `packages/e2e-core/SPEC_NOTES.md:90` states the design rationale: "Why MLS: scales to
  large/dynamic groups, post-compromise security". So **1000 members is within what the crypto
  core supports by design**; nothing in the crypto needs to change.
- However, **no test exercises more than 3 simultaneous members**: `tests/group_membership.rs:41`
  asserts `member_count() == 3` at most; the soak test (`tests/soak.rs:79-108`) churns a
  transient third member over many rounds but never grows the tree. Large-group behavior
  (welcome + serialized `ratchet_tree` size with ML-KEM-768 leaf keys at 1000 leaves — likely
  megabytes per Welcome; commit processing cost) is **untested**. *Hypothesis, not measured.*
- `GroupSession::epoch()` and `clear_pending()` exist in Rust but are **not exposed through the
  uniffi bindings** — `apps/ios/Voiid/Voiid/Networking/GroupEngine.swift:727-729` documents this
  explicitly ("`GroupSession::epoch()` exists only in the Rust core and is not on the uniffi
  surface"). Concurrency recovery is therefore impossible from the apps today.

### 1.5 iOS group implementation

- `apps/ios/Voiid/Voiid/Networking/GroupEngine.swift` — full MLS engine. Documented limitations
  at lines 23-32: **single committer** (concurrent adds/removes conflict); **multi-device same
  user unsupported** (per-user destructive delivery of `/mls/group-events`, lines 26-29); and —
  stale comment but real behavior — MLS add/remove never updates the server-side conversation
  membership (see §2.1).
- Group creation adds each member device sequentially, sending a Welcome to the new user and a
  Commit **to every already-added user** per add (`GroupEngine.swift:260-279`) — O(N²) event rows
  for a group of N. Android does the same (`apps/android/.../net/GroupEngine.kt:246-279`).
- `apps/ios/Voiid/Voiid/Main/GroupInfoView.swift` — the group info screen. Role UI is a **stub**:
  - "Make group admin" / "Dismiss as admin" buttons have **empty closures** (line 51).
  - "Add members" and "Invite via link" rows are empty closures (lines 138-139).
  - "Exit group" only calls `dismiss()` (lines 176-178) — no server or MLS leave.
  - Member removal *is* wired to MLS (`GroupEngine.removeMember`, lines 52-63).
  - Admin badge renders from server role (lines 158-163); members list uses plain `ForEach` in a
    `ScrollView` (lines 141-144) — all rows materialize; at 1000 members this will jank.
- `apps/ios/Voiid/Voiid/Networking/ChatService.swift:33,150` decodes `role` as `String?` (safe
  against absent keys) and maps `isAdmin = role == "admin"`.
- System messages: `MessageKind` includes `.system` (`apps/ios/Voiid/Voiid/Models/Models.swift:30`)
  and `ChatDetailView.swift:1052-1060` renders a centered pill for it — but **the only producer is
  DummyData** (`Models/DummyData.swift:69`). No real event ever creates a system message.

### 1.6 Android group implementation

- `apps/android/.../net/GroupEngine.kt` — mirror of the iOS engine; `addMember` (line 232),
  `removeMember` (line 282), same O(N²) commit fan-out and same absence of server-membership
  updates.
- `apps/android/.../main/GroupInfoView.kt`:
  - "Make group admin" / "Dismiss as admin" **only dismisses the dialog** (lines 176-180).
  - Member add IS wired (`AddGroupMembersScreen` → `chat.addGroupMember`, lines 194-205) — but
    only to MLS, not to the server roster (§2.1).
  - "Exit group" only calls `onBack()` (line 164).
  - **Roles are never displayed from real data**: `ChatService.kt`'s `MemberDTO` (line 31) has no
    `role` field at all, `fetchMembers` (lines 136-145) builds `GroupMemberInfo` without role, and
    `GroupInfoView.kt:85` constructs `VMember(id, name, phone, isYou)` leaving `role` at its
    default `MEMBER`. The admin badge code at lines 284-289 is dead for server data.
  - Members render with `members.forEach` inside a `verticalScroll` Column (lines 155-157) — no
    lazy list; 1000 members will compose 1000 rows.
- `MessageKind.SYSTEM` exists (`model/Models.kt:27`) and `ChatUI.kt:150` renders the centered
  pill — again only fed by `DummyData.kt:64`.
- kotlinx-serialization bug-class note: `CreateGroupBody` correctly uses `@EncodeDefault` on
  `type` (`ChatService.kt:35-37`) — the codebase has already been bitten by encodeDefaults=false;
  any new role/system-event DTOs must keep this in mind.

### 1.7 Group calls today

- Backend `backend/api/src/routes/calls.ts`: `POST /calls/group/token` (lines 144-202) — member-only
  LiveKit JWT, room = `voiid-<conversation_id>`, identity = `user:device`; `POST /calls/group/ring`
  (lines 213-249) — wake-push fan-out to every other active member so calls are discoverable.
  Authorization reads `conversation_members` (lines 169-175) — which makes the server-roster
  divergence in §2.1 a *call-breaking* bug too.
- E2EE: media frames encrypted with a key derived from the MLS exporter secret
  (`GroupEngine.swift:680-697` / `calls.ts:120-125` comment); key rotates on every membership
  commit and live calls re-key via `groupEpochChanged` (`GroupCallService.swift:229-243`).
- iOS UI `apps/ios/Voiid/Voiid/Main/GroupCallScreen.swift`: non-scrolling fill grid (1/stacked/2×2/
  3-wide, lines 150-191), speaking ring, mute badges, mute/video/flip/speaker/leave controls
  (lines 195-233). Android UI `apps/android/.../main/GroupCallScreens.kt`: equivalent overlay,
  weighted non-scrolling rows (lines 200-229), E2EE lock indicator (lines 126-132).
- What the call UI does **not** have, on either platform: an active-speaker/dominant layout or
  paging (at 10+ participants every tile shrinks uniformly — 3 columns × however-many rows on
  iOS, `GroupCallScreen.swift:150-157`), a participant roster sheet, an in-chat "ongoing call —
  Join" banner (discovery is push-only via `/calls/group/ring`; a member who dismisses the
  notification has no way back in except tapping the call button, which *joins*), no
  add-participant-to-call, no PiP for group calls, and no distinct incoming-ring screen (the
  push deep-links straight into join — `VoiidApp.swift:97`, `VoiidMessagingService.kt:87`,
  `DeepLinkRouter.kt:17-19`).

## 2. What is broken or weak (root causes)

### 2.1 CRITICAL — client add/remove never updates the server roster

Neither app ever calls `POST /conversations/:id/members` or `DELETE /conversations/:id/members/:userId`
(grep for `/members` across `apps/ios/**/*.swift` and `apps/android/**/*.kt` returns **zero**
call sites). iOS `addMemberLocked`/`removeMemberLocked` (`GroupEngine.swift:551-616`) and Android
`addMember`/`removeMember` (`GroupEngine.kt:232-307`) do MLS-only work. Root cause: the engines
were written before the membership endpoints landed (the stale iOS comment at
`GroupEngine.swift:30-32` says a backend add-member endpoint "isn't in the current contract" —
it now exists at `conversations.ts:203`).

Consequences for a user added to a group after creation:
- App-message fan-out targets are resolved from `GET /conversations/:id` members
  (`GroupEngine.swift:634-646`, `GroupEngine.kt:311-315`) — the new member is not in the server
  roster, so **no one ever sends them the group's messages** even though they joined via Welcome.
- `POST /calls/group/token` 403s them (`calls.ts:169-175`) — **they can't join group calls**.
- Conversely a removed member keeps their server-roster row active, keeps receiving ciphertext
  they can no longer decrypt, keeps their call access, and still passes the `group-events` member
  check (`mls.ts:62-66`).

### 2.2 No 1000-member cap anywhere

`conversations.ts:101-126` (create) and `203-233` (add) accept unlimited members. The requirement
is a server-enforced cap of 1000. There is also a race in the add path: two concurrent adds each
read the count (once implemented naively) and both insert — the check must lock the conversation
row or use a serialized transaction.

### 2.3 No owner, no role management, role UI stubs

- Schema supports only text roles with no constraint (§1.1); nobody can be promoted/demoted —
  there is no endpoint (§1.2), and both platforms' "Make group admin"/"Dismiss as admin" buttons
  do nothing (`GroupInfoView.swift:51`, `GroupInfoView.kt:176-180`).
- If the sole admin (the creator) leaves via `DELETE /:id/members/:me`, the group becomes
  **admin-less and unmanageable forever** — nothing reassigns admin, exactly the failure Signal's
  model prevents (its server refuses to let the last admin leave without promoting someone;
  clients prompt "choose new admin").

### 2.4 Android shows no real roles at all

`MemberDTO` lacks the `role` field the backend sends (`ChatService.kt:31`), so every member
renders as a plain member (§1.6). Fix must add `val role: String = "member"` — a **default**, not
a nullable-without-default, to avoid the kotlinx absent-key throw, and any *encoded* DTO carrying
`role = "member"` needs `@EncodeDefault` (the receipts/stories bug class).

### 2.5 No in-chat system messages for membership/role events

Both platforms can render `.system`/`SYSTEM` pills (§1.5, §1.6) but no real producer exists.
Nothing announces "X added Y", "X removed Y", "X made Y an admin", or "X transferred ownership".
Root cause: there is no event to render — membership changes happen silently at the SQL layer and
role changes don't exist. Note `messages.ts:60-63` (`assertOpaque`) rejects plaintext-ish payloads
on `/messages/send`, so system events cannot ride the existing message-send path as plaintext;
they need their own representation (see §4 fix 3).

### 2.6 MLS transport does not survive 1000 members (delivery + volume), though the crypto does

- **O(N²) commit rows**: creating an N-member group posts, per added member *i*, a commit row for
  each of the *i-1* prior members (`GroupEngine.swift:271-277`, `GroupEngine.kt:267-273`), inserted
  one row at a time (`mls.ts:69-80`). N=1000 → ~500,000 rows plus 1000 Welcomes each carrying the
  full serialized ratchet tree (with X-Wing/ML-KEM-768 leaf keys, plausibly ~1 MB+ per Welcome at
  1000 leaves — *estimate, unmeasured*, see §1.4).
- **Destructive per-user delivery**: `GET /mls/group-events` marks everything delivered on first
  fetch (`mls.ts:96-102`), so a user's second device silently loses commits — acknowledged at
  `GroupEngine.swift:26-29`. A lost commit permanently kills the group for that device
  (`GroupEngine.swift:37-45`: `max_past_epochs` is 0 and events can't be re-fetched).
- **Single committer**: concurrent admin ops (two admins adding people simultaneously — likely
  with 50 admins) race on the epoch; the reconciliation primitive (`clear_pending`) is not
  exposed to the apps (§1.4).
- **KeyPackage exhaustion**: each device publishes 10 KPs (`GroupEngine.swift:88`); being added to
  a handful of groups drains them, and `GET /mls/keypackages/:user_id` then 409s (`mls.ts:50`) —
  the add silently skips that user (`GroupEngine.kt:252-254` logs and returns). No low-water
  replenishment exists (prekeys have one; MLS KPs don't).
- **Fan-out insert loop**: each group message inserts one `message_ciphertexts` row per recipient
  device in a sequential loop (`messages.ts:95-103`) — 1000+ round-trips per message at target
  scale.

### 2.7 Member list and call grid do not scale visually

- Member lists are non-lazy on both platforms (§1.5, §1.6) — 1000 rows composed eagerly.
- The call grid squeezes all participants into one screen with no active-speaker priority, no
  paging, no roster (§1.7). Fine at ≤8; unusable at 30+.

## 3. How WhatsApp + Signal do it (from Signal source)

### 3.1 Size limits — remote-config'd soft + hard caps, enforced server-side

`Signal-Android/app/src/main/java/org/thoughtcrime/securesms/util/RemoteConfig.kt:587-597`:

```kotlin
private val groupRecommendedLimit: Int by remoteInt(
  key = "global.groupsv2.maxGroupSize", defaultValue = 151, hotSwappable = true)
private val groupHardLimit: Int by remoteInt(
  key = "global.groupsv2.groupSizeHardLimit", defaultValue = 1001, hotSwappable = true)
```

Signal's hard limit is **1001** (1000 others + you), surfaced client-side as `SelectionLimits`
(line 584-585) in every picker, and enforced again by the groups-v2 server when a change is
committed. Takeaway: cap in **both** places — pickers refuse past the limit; the server is the
authority. WhatsApp similarly caps at 1024 today with the server rejecting overflow adds.

### 3.2 Admin model — two roles, changes are group-state mutations with conflict resolution

- Roles are `Member.Role.ADMINISTRATOR` / `Member.Role.DEFAULT`
  (`GroupManagerV2.java:437`) — Signal has **no owner**; any admin can promote/demote any member,
  which is why Voiid's "exactly one owner" needs the extra constraint Signal doesn't model.
- Entry point `GroupManager.setMemberAdmin` (`GroupManager.java:207-216`) → `GroupManagerV2
  .GroupEditor.setMemberAdmin` (`GroupManagerV2.java:430-442`): builds a
  `GroupChange.Actions` role-change action and commits via
  `commitChangeWithConflictResolution` (`GroupManagerV2.java:640-676`) — **up to 5 attempts**; on
  `ConflictException` it re-bases the change onto the current group state (`resolveConflict`) and
  drops it if it became a no-op. This retry-and-rebase loop is the flow-design answer to
  concurrent admin ops that Voiid's single-committer engine lacks.

### 3.3 In-chat role-change messages — derived from the change record, localized client-side

`GroupsV2UpdateMessageProducer.java:909-943` renders update messages from the structured group
change itself, not from server-composed text:

- "…made you an admin" (line 909), "You revoked admin privileges from X" (line 917),
  "X revoked admin privileges from Y" (line 922), "X is now an admin" (line 937),
  "You are no longer an admin" (line 941).

The change record carries editor + target IDs; every client renders its own localized string
("you" vs a name). Takeaway for Voiid: emit a **structured** event
(`{type: role_change, actor_id, target_id, new_role}`) and let clients compose the pill text —
never ship a pre-baked English string.

## 4. Recommended fixes (ordered)

Each is independently actionable. E2EE posture: roles and membership are *already* server-side
plaintext metadata in Voiid (`conversation_members`), so none of this touches message
confidentiality; MLS crypto is untouched per §1.4.

1. **[backend, critical] Sync server roster with MLS membership from the clients.**
   Files: `apps/ios/Voiid/Voiid/Networking/GroupEngine.swift` (addMemberLocked ~551, removeMemberLocked ~591),
   `apps/ios/Voiid/Voiid/Networking/ChatService.swift`, `apps/android/.../net/GroupEngine.kt`
   (addMember ~232, removeMember ~282). Call `POST /conversations/:id/members {user_ids:[…]}`
   before distributing the Welcome, and `DELETE /conversations/:id/members/:userId` after the
   removal commit. Risk: low — endpoints exist and are idempotent (`conversations.ts:203-259`).

2. **[backend] Enforce caps + owner/admin roles in schema and routes.**
   New migration `database/migrations/030_group_roles.sql`: `check (role in ('owner','admin','member'))`;
   partial unique index `create unique index uniq_one_owner on conversation_members(conversation_id)
   where role = 'owner' and left_at is null` (guarantees exactly ≤1 active owner); backfill
   `created_by` → `'owner'` for existing groups. In `conversations.ts`: constant
   `MAX_GROUP_MEMBERS = 1000`, `MAX_GROUP_ADMINS = 50`; count active members inside the create
   transaction and in `POST /:id/members` under `select … for update` on the conversation row
   (avoids the concurrent-add race); creator inserted as `'owner'`. Risk: medium — must treat
   existing `'admin'` creators as owners in the backfill, and `left_at`-reinstates must not
   resurrect a second owner.

3. **[backend] Role-change + ownership-transfer endpoints emitting structured system events.**
   Files: `backend/api/src/routes/conversations.ts`, new migration (can share 030). Endpoints:
   `PATCH /conversations/:id/members/:userId/role {role: 'admin'|'member'}` (owner or admin may
   promote; only owner may demote an admin; reject when admin count would exceed 50) and
   `POST /conversations/:id/transfer-ownership {to_user_id}` (owner-only; atomically demotes self
   to admin and promotes target — single transaction so the one-owner index never trips).
   Emit events as rows in `messages` with `ciphertext = null`, `content_type = 'system'` and a new
   `system_event jsonb` column ({kind:'member_add'|'member_remove'|'role_change'|'owner_transfer',
   actor_id, target_id, new_role}) — the fan-out path already writes null-ciphertext canonical
   rows (`messages.ts:84-89`), and `assertOpaque` (`messages.ts:60`) is bypassed because the
   server itself creates these rows (clients never send them). Publish on `channel:user:*` like
   normal messages. Also emit `member_add`/`member_remove` from the existing membership endpoints.
   Risk: medium — `GET /messages/conversation/:id` consumers must tolerate the new shape.

4. **[both-mobile] Render roles + system messages; wire the stub actions.**
   Android: add `val role: String = "member"` to `MemberDTO` (`ChatService.kt:31` — default value,
   not bare nullable, per the kotlinx absent-key rule), thread it through `fetchMembers`
   (lines 136-145) into `GroupInfoView.kt:85`, show owner/admin badges (lines 284-289), and make
   the dialog buttons (lines 176-190) call the new PATCH endpoint. iOS: map `role == "owner"`
   in `ChatService.swift:150`, fill the empty closures in `GroupInfoView.swift:51` (promote/demote),
   `:138` (add members — engine call exists), and make "Exit group" (`:176`) actually call
   `DELETE /:id/members/:me` + MLS self-handling; block owner exit until ownership is transferred
   (prompt to pick a successor — Signal's "choose new admin" flow, §3.2). Both: map
   `content_type == 'system'` + `system_event` into the existing `.system`/`SYSTEM` pill renderers
   (`ChatDetailView.swift:1052`, `ChatUI.kt:150`), composing localized text client-side (§3.3).
   Risk: low-medium.

5. **[backend + both-mobile] MLS transport scaling — delivery, not crypto.**
   (a) Migrate `mls_group_events` to per-**device** delivery (`recipient_device_id` column +
   per-device delivered marks) — fixes the second-device commit loss (`mls.ts:96-102`,
   `GroupEngine.swift:26-29`). (b) Store ONE commit row per (conversation, epoch) with a
   delivery-tracking table instead of N copies — collapses the O(N²) creation cost (§2.6).
   (c) Batch inserts (`unnest`) in `mls.ts:69-80` and `messages.ts:95-103`. (d) KeyPackage
   low-water replenishment: return remaining count from `POST /mls/keypackages`, add
   `GET /mls/keypackages/count/:device_id`, clients top up like prekeys. Files:
   `backend/api/src/routes/mls.ts`, `backend/api/src/routes/messages.ts`, new migration,
   `GroupEngine.swift`, `GroupEngine.kt`. Risk: medium-high (delivery semantics change; keep
   backward compatibility for already-stored rows).

6. **[all] Concurrency + scale validation for MLS at 1000 (no crypto changes).**
   Expose `GroupSession::epoch()` and `clear_pending()` through the uniffi bindings
   (`packages/e2e-core/src/api.rs` / regenerated `apps/ios/Voiid/Voiid/voiid.swift`,
   Android bindings) so apps can implement Signal-style rebase-and-retry (§3.2) for concurrent
   admin commits (`group.rs:350-370` already documents the contract). Add an `#[ignore]`d
   1000-member soak test in `packages/e2e-core/tests/` measuring welcome/ratchet-tree sizes and
   commit-processing time (§1.4 gap). Client pickers cap selection at 999 others (Signal
   `SelectionLimits` pattern, §3.1). Risk: low — additive.

7. **[both-mobile, backend] Group call UI overhaul.**
   iOS `GroupCallScreen.swift` + `GroupCallService.swift`, Android `GroupCallScreens.kt` +
   `GroupCallManager.kt`, backend `calls.ts`:
   - Active-speaker layout past 8 participants: dominant tile + paged thumbnail strip instead of
     the uniform shrink (`GroupCallScreen.swift:150-191`, `GroupCallScreens.kt:200-229`); keep the
     never-scroll rule for ≤8.
   - Participant roster bottom sheet (names, mute/video state, speaking) — data already exists in
     `GroupCallParticipant` (`GroupCallService.swift:40-64`) / `GroupCallManager.Participant`.
   - In-chat "ongoing call — Join" banner: add `GET /calls/group/active?conversation_id=` backed
     by a short-TTL Redis key refreshed by connected clients (or LiveKit webhook), so discovery
     isn't push-only (§1.7); render the banner in `ChatDetailView.swift` / `ChatDetailView.kt`.
   - Incoming group ring UI (accept/decline card from the `group_call` push instead of instant
     deep-link join — `VoiidApp.swift:97`, `VoiidMessagingService.kt:87`).
   - Convert member lists to lazy lists while in there (`GroupInfoView.swift:141-144`,
     `GroupInfoView.kt:155-157`).
   Risk: medium — pure UI + one small backend endpoint; E2EE path (`callKeyPassphrase`,
   epoch-rekey) untouched.
